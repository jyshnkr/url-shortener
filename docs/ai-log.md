# AI-human traceability log

Selected discussions, decisions and corrections, in the order the work developed. Each entry separates the human contribution, the AI contribution and the resulting change. Detailed checks and measurements are recorded in the [testing document](testing.md).

| Key moment | Human contribution | AI contribution | Result |
| --- | --- | --- | --- |
| **Build the service in manageable steps** | Asked for small, reviewed changes and a service that others could run and understand. | Built the application foundation, database setup and isolated tests. | A working local foundation with repeatable startup and verification. |
| <a id="tomcat-patch-decision"></a>**Review a proposed security update** | Asked why the web-server library needed updating, then approved the change. | Explained the security findings, applied the approved update and checked startup. | The project used the approved patched version and still started successfully. |
| **Correct a commit made without approval** | Clarified that asking for advice did not authorize a commit. Requested a correction to the log. | Acknowledged the mistake and corrected the approval record. | The log accurately recorded the unauthorized action. The existing commit was left unchanged as requested. |
| **Correct problems found during creation testing** | Approved testing that covered invalid input, simultaneous requests, restarts and database failures. | Tests and review exposed excessive waiting on an unresponsive database and acceptance of malformed text. Reproduced and corrected both problems. | Database waits had defined limits, malformed addresses were rejected, and the checks covering those failures passed. |
| **Simplify link creation** | Questioned the extra identifier required from callers and chose to reuse links for identical destinations. | Explained the options, changed creation behavior and preserved existing saved links. | Callers submit only a destination; repeated submissions return its saved short link. |
| **Give the code clearer responsibilities** | Requested separation of concerns and a clear responsibility for each part. | Separated validation, configuration and storage setup from creation decisions. | Request handling, creation logic, validation, code generation and database work had clearly defined responsibilities. Existing behavior checks passed. |
| **Make saved links work when followed** | Required redirects to preserve accepted destinations, including long addresses and international characters. | Built redirection. Testing exposed a response-size limit affecting long addresses; adjusted it without changing saved destinations. | Redirects worked for the tested addresses, including after restart. Missing links and database failures produced clear errors. |
| **Prioritize automatic checks** | Deferred additional features and prioritized quality and security checks. | Added the checks. Review also found and corrected a gap that could hide secrets in older files. | Repeatable checks covered code, behavior, dependencies and exposed secrets, including project history. |
| **Measure performance honestly** | Approved a specific workload and required failed results to remain visible. | Built the measurement check, corrected a startup mistake and retained its failure evidence before completing a valid run. | The local speed target passed. The report clearly separated the setup failure from the measured result. |
| **Fix the failed security run** | Reported the failure, clarified that the diagnosis had been understood as an applied fix, and requested the change. | Explained that the fix had not yet been applied, then reproduced and corrected the report-writing problem. | Security tools could save their reports, and the subsequent hosted checks passed. |
| **Bring usage statistics into scope** | Brought analytics forward, approved its rules, then reviewed and pushed the implementation. | Built statistics and background recording, including checks for slow, failed and overloaded recording. | Recorded usage became available while valid redirects continued through recording failures. Counts can still be incomplete during failures. |
| **Make documentation understandable** | Requested plain language, reviewed table-based scenarios and reinforced review before edits. | Acknowledged starting a temporary draft too early, then presented drafts for review and applied the approved versions. | Three scenario documents now share the agreed structure, language and evidence format. |
